# MacBookPro13,3 mobile profile

See [the investigation](stability-2026-09-09.md) for measured results and outstanding checks. This profile is an explicit add-on to an existing kit installation, with `linux-lts` and `linux-lts-headers` already installed and an LTS entry generated by Omarchy.

```bash
sudo ./scripts/install-mobile-profile
./scripts/macbook-t1-chromium-config
sudo reboot
```

The installer preserves the existing autologin, SSH, Wi-Fi and disk-unlock choices. It changes the legacy lid-hibernate flag to zero and adds later systemd drop-ins for suspend on lid close, on either battery or AC. Docked lid close remains ignored. The remote-maintenance lid override must be disabled before installing this profile.

Sleep uses S3 (`deep`), synchronous device callbacks and temporary unloading of the unused Thunderbolt NHI module. `macbook-t1-sleep` selects the mode itself for every cycle; the systemd sleep drop-in leaves `MemorySleepMode` unset so systemd does not override it. `OMARCHY_SLEEP_MODE=deep|s2idle` in `/etc/macbook-t1-omarchy.conf` sets the preferred mode (default `deep`). The `macbook-t1-tb-nod3` DKMS module keeps both Alpine Ridge upstream bridges and USB-C xHCIs in D0 across sleep; with that, both USB-C trees survive S3 on battery and on the charger, and no PCI remove/rescan is needed. Removing the trees before S3, as earlier versions did, made the first S3 on a charger return after 3–4 s and lose both controllers. The same module forbids runtime PM on both USB-C xHCIs once `xhci_hcd` binds, at boot and after a rescan, because they miss hot-plug events while runtime-suspended. The helper unloads and reloads `brcmfmac` around sleep and suspends again after 5 s if the lid is still closed. A very short S3 (a few seconds) leaves both Alpine Ridge controllers unpowered; the next sleep then removes what is left of the dead trees before S3 and rescans after wake, which brings them back after a sleep of a few minutes. With a USB device attached to a USB-C port the helper uses s2idle for that cycle, because firmware leaves that controller unpowered after S3 until the next power-off; it then sets a 10-minute RTC alarm so a later cycle can switch to S3 once the device is unplugged. The `macbook-t1-socw` DKMS module calls `ASOC.SOCW(1)` after every resume, and the helper sends `SOCW(0)` through the module's `socw` parameter as the last step before S3, as macOS does; without the wake message the T1 keeps the Touch Bar dark after S3.

After resume the helper runs Omarchy's own `omarchy-system-wake` command in each active graphical user session. The firmware lid event wakes the machine, while this step turns the panel on and reconciles its monitor state without waiting for a keyboard event. The lock remains active.

Closed-lid preparation switches the built-in card (`alsa_card.pci-0000_00_1f.3`) to the `off` profile in each user's PipeWire session and restores the saved profile after wake. This closes every CS8409 PCM, which runs the out-of-tree codec driver's speaker-amplifier shutdown (its Mac-specific suspend callback is a no-op), while applications keep their PipeWire connections. Earlier versions stopped the PipeWire units instead; browsers then lost microphone and speakers until restarted (Teams: "no mic found"). The helper waits up to 5 s for the PCMs to close and refuses sleep if a CS8409 stream stays open.

The local libinput quirk classifies this model's `Apple SPI Keyboard` as internal. Its reported vendor ID does not match the generic Apple SPI rule, which prevents reliable keyboard/touchpad pairing for disable-while-typing. The quirk is model- and device-name-gated and leaves pointer acceleration, scrolling, tapping and the touchpad's existing size-based palm detection unchanged. The maintained Hyprland input block also explicitly enables disable-while-typing and disables tap-and-drag, preventing an accidental palm tap from turning subsequent motion into a window drag. Pointer speed remains at the normal zero setting; tapping, physical clicks and scrolling remain available. The maintenance hook restores this marked block after Omarchy updates.

The installed `xdg-desktop-portal-hyprland` 1.4.1 backend has an upstream-reported busy loop when PipeWire restarts before a later screen-share request. This machine deliberately restarts PipeWire around closed-lid sleep to close the unsafe CS8409 audio stream. A systemd user drop-in therefore makes the Hyprland portal `PartOf=pipewire.service` and orders it after PipeWire. It reconnects whenever PipeWire itself is restarted. A live restart verified new PipeWire and portal processes, active audio/portal services and a responsive portal D-Bus interface. This is a local mitigation for the reproduced trigger, not an upstream source fix or a claim that all screencast failures are prevented.

The suspend diagnostic drop-in records battery charge, voltage, elapsed time, SLP_S0 residency, wake IRQ and changed ACPI GPE counters for each cycle. Its average-watt figure is an estimate from the battery telemetry, including entry and exit overhead. It is emitted only when both endpoints report discharging and charge has not increased; even that does not independently exclude a power connection between samples. A SLP_S0 percentage is meaningful only when the counter is valid for this platform. The observed value 446676598680 equals 0xffffffff multiplied by the driver's 104 us tick; it is treated as unavailable rather than 0% residency. Battery drain and working session recovery remain the acceptance criteria. Package residency comes from separate CPU MSRs and is retained as diagnostic evidence.

On the tested machine, a lid test remained in one uninterrupted s2idle cycle for 5,409 seconds. It resumed the same boot and Hyprland process and recorded a net loss of 61 mAh. The original 0.515 W estimate is not accepted as a clean battery-only reference: reinspection on 30 September found `Discharging` at entry but `Charging` at the post sample, and an ADP1 event-count increment. The timing and contribution of external power are not established by those endpoints. Both Alpine Ridge xHCI controllers and their drivers remained present, Wi-Fi reconnected, the Touch Bar services were active and systemd recorded zero suspend failures.

A later real-world bag cycle on 22 September stayed in one s2idle operation for 11,689 seconds but lost 2,314 mAh, an estimated 8.660 W. Its ACPI `GPE17` count rose by 192, compared with 10 during the preceding quiet cycle. The machine's DSDT maps `_L17` directly to a wake notification for `SPI1.SPIT`, the Apple SPI keyboard/touchpad. This is why closed-lid Apple SPI wake is suppressed alongside xHCI wake.

The first overnight retest then entered s2idle at 20:36 with 55% charge and did not resume: the next boot at 09:02 followed complete battery depletion and an unclean shutdown. Pre-sleep evidence proves Apple SPI and all three xHCI wake paths were disabled, LID0 alone remained enabled, user processes froze and the network shut down. The missing post phase prevents an exact average measurement, but exhausting roughly 39 Wh within at most 12 hours 26 minutes implies at least about 3.1 W. Unlike the earlier low-draw test, this cycle started from a working desktop with applications active. Inspection then identified the CS8409 no-op suspend callback. The audio-quiesce transaction is the targeted follow-up; it passed a live open-stream close/restore test, but still requires a disconnected lid duration test before sleep drain can be considered fixed.

The 25 September follow-up resumed the same boot and Hyprland process after 7,298 seconds, but lost 413 mAh, an estimated 2.514 W. The USB Ethernet adapter was still attached to the left Alpine Ridge xHCI controller, so this was not the requested disconnected baseline. It had no intermediate wake. Its originally reported 0% SLP_S0 is withdrawn: the constant all-ones register value does not establish actual residency. PMC counters also showed no package C6/C7/C8/C9/C10 residency anywhere in the boot, although individual CPU cores used C10. The FADT says both Low Power S0 Idle and platform PCIe ASPM support are absent, and both Thunderbolt root links consequently report ASPM disabled. The diagnostic hook saves package C-state counters and enables the Intel PMC failed-S0ix report only when its counter passes the invalid-value check. The firmware flags and disabled links are observations, not proof that ASPM causes the drain. No forced-ASPM experiment has been applied.


## Evidence correction and recovered duration test, 30 September 2026

Live checks still show Omarchy 4.0.4-1 and kernel 6.18.49-3-lts. The PMC is Sunrise Point-H PCI 8086:a121. Upstream's Skylake PMC initialization checks for Sunrise Point-LP 8086:9d21 and otherwise uses a Cannon Lake register map. This is a plausible explanation for the all-ones MMIO readings on this machine; the installed driver mapping has not been independently instrumented. The recorded SLP_S0 value is exactly 0xffffffff × 104, and the earlier LTR readings were also all ones. Therefore neither zero S0ix residency nor all-Yes PMC status is accepted as evidence. The FADT's missing Low Power S0 Idle declaration also does not, by itself, prove that low-power idle is impossible.

Retained logs supply the disconnected test that had been considered pending. USB Ethernet disconnected at 15:25:26 on 25 September. The lid closed at 15:29:03, s2idle entered at 15:29:05 and returned at 20:17:26 when the lid opened. The diagnostic interval was 17,303 seconds. Charge dropped from 6,174 to 1,755 mAh (93% to 26%), yielding an estimated 10.281 W; battery temperature rose from 33.5 to 41.5 °C. The logs show closed CS8409 PCM streams, disabled xHCI/SPI wake permissions and masked GPE17 before entry. There is one suspend/resume cycle, with GPE17 increasing by one. Thus USB Ethernet attachment, open audio streams and repeated full resumes cannot explain this particular failure alone. Package-C3 increased, while the recorded package-C6 through C10 counters remained zero. The component responsible for the remaining power draw is unresolved.

The diagnostic correction is covered by fixture tests for invalid counters at entry or resume, valid zero/progressing counters, retained battery/package evidence and restoration of the PMC warning setting. It changes measurement interpretation, not sleep power behavior.

Sources: [Linux 6.18 PMC register scaling](https://github.com/torvalds/linux/blob/v6.18/drivers/platform/x86/intel/pmc/core.c), [Skylake PMC register-map selection](https://github.com/torvalds/linux/blob/v6.18/drivers/platform/x86/intel/pmc/spt.c), [PMC IDs and counter step](https://github.com/torvalds/linux/blob/v6.18/drivers/platform/x86/intel/pmc/core.h).

### Targeted driver investigation, 30 September 2026

The current NHI workaround has a concrete power-management tradeoff. In upstream Linux 6.18, `nhi_remove()` takes a runtime-PM reference and forbids runtime PM before shutting down the controller's rings. With the driver removed, `pci_pm_suspend_noirq()` follows its `!pm` branch, saves configuration and jumps past `pci_prepare_to_sleep()`. Thus unloading NHI does not itself put these PCI functions into D3hot. This is a candidate contributor, not an attribution of the measured 10 W. Both NHI functions (`06:00.0`, `7c:00.0`, Intel `8086:15d2`) were D0 while awake with their driver bound.

The Radeon debug register at selected port 0x50 read `00 01 00 00` while PCI sysfs still said D0. A gmux power write and Linux's cached PCI state are separate; the D0 label alone must not be called proof that the Radeon rails are on. The upstream gmux suspend callback disables interrupts; its resume callback only reasserts off when its own cached switcheroo state is off. Debugfs writes do not update that cached state. Physical rail power during the sleep interval remains unmeasured.

The installed Apple CS8409 suspend callback is a no-op, as previously found, but the HDA controller was runtime-suspended in D3hot during this inspection. PCM closure, HDA controller power and amplifier power must be distinguished; this finding neither proves nor excludes an amplifier contribution.

Snapshot 52 was created before a targeted trace. A separate ftrace instance `macbook_sleep_20260930` records power callback events and two kprobes: the PCI state after `pci_pm_suspend_noirq()` and requested states at `pci_set_power_state()`. Structure offsets were read from the running kernel's BTF, not assumed across kernels (6.18.49-3-lts: `pci_dev.dev=200`, `current_state=160`, `device.kobj.name=0`). No new power policy was enabled. A one-shot `macbook-sleep-baseline-20260930` service armed a 30-second RTC alarm and requested normal systemd suspend. The first runner was defective: `systemctl suspend` returned after enqueueing the request, so its EXIT cleanup disabled the RTC alarm and tracing before actual suspend. The empty trace and the journal prove this ordering. This was a test-harness failure, not evidence of broken RTC wake. The corrected runner uses `systemctl start --wait systemd-suspend.service`, retaining the alarm and trace until the oneshot suspend job finishes.

Trace and identity comparison files are under `/var/lib/macbook-t1-omarchy/sleep-investigation-20260930` on the laptop. On reconnection, retrieve the trace, compare boot and compositor identities, check the service result, then disable/delete only this trace instance and its two namespaced probes. The corrected script saves the trace and clears its alarm only after the suspend service finishes; a reboot loses in-memory trace evidence. The first sleep ran from 15:59:43 to 16:08:01 in s2idle and retained the same boot and Hyprland PID. Kernel timing attributes 6.228 seconds to bridge 04:00.0 and 6.220 seconds to bridge 7a:00.0 during noirq resume (12.626 seconds for the phase). The corrected baseline ran at 16:10:29 and returned automatically at 16:11:14, with 28.301 seconds in the traced machine-suspend interval. This validates the corrected RTC test runner. Both external xHCI controllers and HDA had cached state 3 (D3hot); both NHI functions had state 5 (unknown), not confirmed D3hot; the Radeon graphics function had state 4 (D3cold).

An awake follow-up read actual NHI PMCSR after driver removal: both were `0008`, meaning D0 with NoSoftRst set. A bounded test wrote only the power-state bits (with PME-status writes suppressed), read back `000b` (D3hot), retained access to both USB controllers, restored `0008`, and successfully rebound both NHI drivers. This proves an awake D3hot round trip, not energy savings or the exact state throughout earlier suspends. A one-shot sleep experiment subsequently uses a runtime-only systemd drop-in to park those two already-unbound endpoints and restores D0 before the normal post helper rebinds them; its runner removes the drop-in after the job completes. Parent bridges, ASPM and the normal installed sleep policy are unchanged. The modified sleep test ran 16:14:15–16:15:00, resumed automatically, preserved the original boot/Hyprland process, restored all four NHI/xHCI driver bindings, and removed its runtime drop-in and saved state. Resume still spent 6.261 and 6.218 seconds in the two upstream bridges, so this experiment did not fix wake latency. A full power estimate still requires a battery-only test; AC-connected callback tracing cannot establish it. A paired baseline/D3hot 90-second-per-cycle runner is prepared under the same private investigation directory and checks for a discharging battery, absent USB Ethernet, and at least 20% charge before either measurement. No power-saving benefit has yet been measured. The updated battery diagnostic was deployed with SHA256 `ab7967a88616ad8b61c11154f225e56461c57c6a3637588c29dd2f36b2da67c6`; its predecessor is backed up in that directory.

Sources: [PCI system-suspend handling](https://github.com/torvalds/linux/blob/v6.18/drivers/pci/pci-driver.c), [NHI removal and suspend](https://github.com/torvalds/linux/blob/v6.18/drivers/thunderbolt/nhi.c), [gmux power and sleep callbacks](https://github.com/torvalds/linux/blob/v6.18/drivers/platform/x86/apple-gmux.c).

### Battery crossover test, 30 September 2026

After the user disconnected power and USB Ethernet, four RTC-woken cycles ran from an open-lid desktop. Both endpoints of every cycle reported Discharging. The first pair is archived as `pair-1` under the private investigation directory; the reverse-order pair remains in its top-level `battery-*` files.

| Order | NHI handling | Measurement interval | Recorded charge loss | Estimated average including entry/resume |
| --- | --- | --- | --- | --- |
| 1 | Existing unbind/rebind | 105 s | 29 mAh | 11.340 W |
| 2 | Temporary D3hot | 106 s | 15 mAh | 5.796 W |
| 3 | Temporary D3hot | 108 s | 29 mAh | 10.971 W |
| 4 | Existing unbind/rebind | 105 s | 14 mAh | 5.452 W |

Each traced machine-suspend interval was approximately 88 seconds. The apparent benefit in the first pair reversed when the order reversed. Across the two windows for each setting, the elapsed-time-weighted estimate is approximately 8.40 W for baseline and 8.41 W for D3hot, including preparation and resume overhead. These short measurements do **not** establish an NHI power-saving benefit. The normal sleep policy therefore retains its prior behavior; the experimental override and state were removed. All four NHI/xHCI functions were accessible with the correct drivers, the original boot and compositor survived, the RTC alarm was empty, and no system units had failed. The isolated ftrace instance and all four namespaced kprobes were removed after collection.

The ACPI timing probes independently localized virtually all of the long resume delay to `acpi_pci_set_power_state(..., D0)` for upstream bridges `04:00.0` and `7a:00.0`, approximately 6.22 seconds each under either NHI setting. This narrows the latency issue to their firmware power transition; it does not identify the cause of overnight drain. A read-only awake battery check sampled at approximately two-second intervals. Charge and current changed at that cadence, and the kernel battery cache parameter is 1000 ms. Thus a simple minute-long battery-cache explanation was not reproduced while awake; behavior across the suspend boundary and the first/second-window pattern remain unresolved. Do not present either short estimate as steady-state sleep wattage or use this test to declare the overnight issue fixed.

The existing Touch Bar driver omits its normal-resume callback and waits for a separate display interface that T1 hardware does not provide. The add-on patches the installed DKMS source to call resume and use the same T1 interface requirement as initial activation, then rebuilds it for installed kernels with headers. Reset-resume still restores its USB runtime-PM reference; normal resume preserves that reference. The driver source backup remains on the laptop. Package updates trigger the repair again if they replace the source; an unexpected source layout produces an error for review instead of an approximate patch.

`macbook-t1-touchbar-display.service` also follows the internal panel's actual DRM DPMS state. When the panel switches off, it uses the driver's live `idle_timeout=-2` control to deactivate the Touch Bar. When the panel comes back on, it restores the previous Touch Bar setting. A one-second polling interval handles both automatic idle and manual display changes. The service saves its temporary override under `/run`, restores it on a clean stop and does not reconfigure USB or reload the driver. The keyboard and trackpad can wake the screen normally.

The ordinary boot blacklists amdgpu, pins Hyprland to Intel and powers the unused Radeon off through Apple GMUX after the desktop starts. The generated kernel command line also selects s2idle and prevents the unused Radeon HDMI-audio function from binding before PipeWire starts. The power-off helper checks that Intel owns the internal panel, Hyprland is pinned to Intel and Radeon audio is unbound before changing the GMUX rails. It repeats this after wake.

The maintenance helper also preserves a small guard in Omarchy's per-key focus-border callback. Without it, every key press and auto-repeat reapplies the same Hyprland border configuration even when the border is already hidden. The guard makes unchanged key events return immediately and is reapplied after a recognized Omarchy update.

The boot check also protects against Apple firmware resetting the startup GPU preference after a fully depleted battery or NVRAM reset. If an Intel-only boot has no internal panel and the EFI preference points elsewhere, it restores the Intel preference and performs at most one automatic recovery reboot. A persistent attempt marker prevents reboot loops; a successful Intel display boot clears it.

The preferred boot entry copies the generated LTS protocol, image path, hash and command line after verifying the image's BLAKE2 hash. The same helper points Safe Graphics and Console at the installed `linux-omarchy` image and refreshes their hashes. An image rebuild refreshes all three entries automatically. Snapshot entries remain available.

The maintenance helper limits Limine to two snapshot entries. It excludes the removed ordinary `linux` kernel and the redundant rescue kernel from snapshot submenus, leaving one LTS route per retained snapshot. This does not itself delete Btrfs snapshots; snapshot retention remains an explicit administrative choice.

Chromium renders on the Intel GPU through ANGLE OpenGL and decodes video with Intel VA-API (iHD: H.264, HEVC, VP8; not VP9 or AV1). `macbook-t1-chromium-config` removes the old `--disable-accelerated-video-decode` from the Radeon era and adds the Wayland VA-API features to `--enable-features`, keeping other user flags, with a timestamped backup. A 1080p60 H.264 test video dropped from 410% to 146% Chromium CPU and from 18.6 to 15.7 W on battery. It also loads the vendored `chromium/enhanced-h264ify` extension (MIT, installed to `/usr/local/share/macbook-t1/chromium`), so YouTube serves H.264 instead of VP9/AV1, at most 1080p: the same 60 fps YouTube video in a half-screen window used 168% Chromium CPU without it and 87% with it. `macbook-t1-omarchy-maintain` reruns the script after Omarchy updates, because Omarchy can rewrite `chromium-flags.conf`. Close and reopen Chromium and its web apps to load changed flags.

## Touch Bar visible but buttons ignored, 2 October 2026

The user clarified that the panel had resumed visually but its buttons did nothing. Touch Bar-only input monitoring recorded key events, and a bounded dynamic-debug check exposed `want_mode=2` with `cur-mode=3`: the driver wanted media-key mode but still believed the bar was off. The T1 branch of `appletb_set_tb_mode()` returned the byte count from its one-byte `usb_control_msg()`, while `appletb_set_tb_worker()` updates `cur_tb_mode` only for a zero result. Following suspend, the cached off state therefore remained and the input handler suppressed normal keys. The previously added normal-resume callback did not correct this separate return-value bug.

The maintained patch now converts a successful one-byte T1 transfer to zero, preserves negative USB errors and rejects short/unexpected transfers with `-EIO`. The T2 branch is unchanged. This follows the [USB control-message return contract](https://docs.kernel.org/driver-api/usb/usb.html#c.usb_control_msg). Source migration is guarded and idempotent, including upgrades from the earlier resume-only patch; four fixture tests pass. Unknown source layouts fail without rewriting the source.

Snapshot 53 and the old module, source and helper were saved before installation. DKMS rebuilt both installed kernels, UKIs and Limine hashes were refreshed and verified, and only `apple_touchbar` was reloaded. An awake off/on round trip then reached `cur-mode=3` when off and `cur-mode=2` when on; the boot and compositor identities remained unchanged. The user subsequently confirmed that the Touch Bar buttons work again. A later normal sleep/resume with the corrected driver still requires verification. This repair does not establish a fix for battery drain.

## Reverting

The installer saves existing affected files under `/var/lib/macbook-t1-omarchy/mobile-backup-*`. The investigation records root snapshots separately. `/boot` is a separate filesystem and is not covered by the root snapshot; Limine config backups are also stored beside the live file.

To revert browser settings, restore the relevant `~/.config/chromium-flags.conf.before-macbook-video-*` backup and restart Chromium.

To stop following the internal screen, run `sudo systemctl disable --now macbook-t1-touchbar-display.service`. Stopping the service restores the Touch Bar setting it temporarily changed; a newer setting written by the user is preserved.

To stop powering off the Radeon after Intel starts, disable `macbook-t1-radeon-off.service`, remove the service and helper, then reload systemd. Reverting the complete Intel-only setup also requires restoring the prior Hyprland GPU choice, removing `module_blacklist=amdgpu` from the generated command line and rebuilding both kernel images.

To stop preferring LTS, remove `/etc/boot/hooks/post.d/81-macbook-t1-preferred-kernel` and the marked `MacBook T1 preferred kernel` block from `/boot/limine.conf`. Retain its ordinary generated `//linux-lts` entry if the package remains installed. The kit's default-entry guard will choose the first remaining entry.

The mobile sleep files are:

- `/etc/systemd/logind.conf.d/91-macbook-t1-suspend.conf`
- `/etc/systemd/sleep.conf.d/91-macbook-t1-deep.conf`
- `/etc/systemd/system/systemd-suspend.service.d/90-macbook-t1.conf`
- `/etc/systemd/system/systemd-suspend.service.d/95-macbook-sleep-diagnostics.conf`
- `/usr/local/sbin/macbook-t1-sleep`
- `/usr/local/sbin/macbook-sleep-diagnostics`
- `/etc/libinput/local-overrides.quirks`

Review the remaining lid policy before removing these files: a legacy `90-macbook-t1-mobile-lid.conf` may still request the hibernation mode that failed in testing. Use `systemd-analyze cat-config systemd/logind.conf` and `systemd-analyze cat-config systemd/sleep.conf` to see the complete policy. Reload systemd and reboot after reverting it.

To revert the driver change, first remove `/usr/local/sbin/macbook-t1-touchbar-resume-fix`, then reinstall `t1-touchbar-dkms`, regenerate the kernel images and reboot. Removing the helper prevents the kit's package hook from immediately reapplying the patch. This restores the original driver, including its missing normal-resume callback and incompatible T1 resume readiness check.

## One-shot firmware trace, armed 30 September; unresolved outcome checked 2 October

The next attempt started at 16:55:35 on 30 September. Its last retained service message reports freezing `user.slice`; no post hook result or `firmware-methods.trace` was saved. The next retained boot starts at 21:18. There is insufficient evidence to attribute the interrupted session to battery depletion, manual reset, the measurement probes or another failure. The runtime override and probes are absent after reboot. Do not reuse the instrumented sleep attempt without investigating this incomplete outcome. The awake preflight below did not validate tracing across actual suspend.

The later uninstrumented overnight cycle, 1 October 21:53 to 2 October 09:06, resumed the same boot and compositor but lost 62 percentage points of battery charge (67% to 5%; 4,140 mAh over a 40,384-second diagnostic interval). The post sample was charging, so the power estimate was correctly withheld. Both bridge noirq resume callbacks again took approximately 6.22 seconds each. See the dated Dutch analysis for the full evidence and Touch Bar status.

Inspection of this machine's SSDT7 shows that the Thunderbolt upstream-bridge `_PS0` method calls `PCED` followed by two `CRMW` operations on the Darwin firmware branch. `PCED` contains PCIe link recovery waits; `CRMW` retries controller configuration reads/writes through `CIOR` and `CIOW`. Either path could account for the measured delay. The outer ACPI call timing does not distinguish them and does not establish their contribution to battery drain. No firmware power method was manually invoked and no ACPI table, OS identity, ASPM setting or sleep policy was changed.

A private diagnostic helper, `trace-firmware-once`, is stored beside the other evidence under `/var/lib/macbook-t1-omarchy/sleep-investigation-20260930`. It is gated to MacBookPro13,3 and the verified `6.18.49-3-lts` kernel. Namespace-node name/parent offsets and the method object's node offset were checked against the running kernel's BTF. Isolated kprobes on `acpi_ds_begin_method_execution` and `acpi_ds_terminate_control_method` record only selected method/ancestor names and timestamps, plus suspend phase markers. An awake `_LID` read verified a matching begin/end pair and successful probe/instance cleanup. Battery sysfs reads did not produce a `_BST` pair in that preflight and were not used to claim validation.

The runtime-only drop-in `/run/systemd/system/systemd-suspend.service.d/98-macbook-acpi-once.conf` arms collection for the next ordinary suspend. No probes remain active while waiting. Diagnostic errors are nonfatal to the suspend service. After that attempt, the post hook saves `firmware-methods.trace`, per-CPU buffer statistics and a completion timestamp in the private evidence directory, removes its probes and trace instance, deletes the drop-in and reloads systemd. A reboot also clears the runtime arming. No suspend or reboot was initiated while preparing this measurement. On the next user-confirmed return, inspect overflow statistics and paired method durations before proposing a firmware workaround. To cancel before sleep, remove only that drop-in and run `systemctl daemon-reload`.

The brightness keys keep Omarchy's own steps from 1% up and add 0.8, 0.6, 0.4 and 0.2% below 1% for dark rooms (`/usr/local/bin/macbook-t1-brightness-control`, idea from mrdrbrdr/advanced-brightness-control-omarchy). Above 1% it hands each key press to `omarchy-brightness-display`; below 1% it sets the gmux backlight itself and shows the value in Omarchy's OSD. `macbook-t1-omarchy-maintain` keeps the marked `MacBookPro13,3 T1 brightness` block in `~/.config/hypr/bindings.lua` after Omarchy updates, and removes it with a warning if one of the Omarchy commands it relies on disappears, so the keys fall back to Omarchy's defaults.
